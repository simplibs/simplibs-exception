# 📦 `testing/asserts/fields`

**Field-Level Exception Assertion Engine**

The `asserts/fields` package contains the fundamental building block 
of the entire **SimpleException** testing infrastructure:

**the granular validator for individual exception fields**.

It represents the lowest layer of the testing system, upon which 
all higher-level testing pipelines are constructed:

* `assert_exception_class` (Exception class testing)
* `assert_exception_function` (Testing functions that raise exceptions)
* `bulk_test` (Automated test generation)

## 📁 Package Contents

* `assert_exception_fields.py`

## 🧭 Core Architectural Solutions

### 1) Granular Validation of Individual Exception Attributes

Every exception instance carries a specific set of telemetry attributes:

* `error_name`
* `label`
* `message`
* `expected`
* `value`
* `problem`
* `context`
* `how_to_fix`
* `exception`
* `get_location`
* `skip_locations`
* `oneline`

The `assert_exception_fields` utility allows you to **selectively** validate any subset of these attributes.

This design is critical because:

* Some tests isolate and check a single attribute.
* Some audit the entire object state.
* Some only verify mutations against default values.
* Some focus exclusively on dynamic runtime behavior.

---

### 2) Support for Fuzzy, Prefix, and Exact Match Comparisons

Textual attributes (e.g., `message`, `problem`, `context`) are often:

* Dynamic and context-dependent.
* Multi-line sequences.
* Generated by layout engines.
* Rich in metadata or stack traces.

To handle this, the package provides a **Multi-Modal Evaluation Hierarchy**:

* **`exact_match=True`** $\rightarrow$ Absolute equality verification.
* **`startswith=True`** $\rightarrow$ Prefix-based validation.
* **Default Mode** $\rightarrow$ Fuzzy substring inclusion lookup.

This prevents tests from becoming brittle and failing over minor layout or formatting mutations.

---

### 3) Conditional Subtests via `maybe_subtest`

Each telemetry attribute can be validated within its own isolated boundary:

* **Verbose Mode:** Every property check runs inside a dedicated native pytest subtest.
* **Silent Mode:** Standard assertions execution without subtest overhead.

This architectural choice enables:

* Clean, isolated error readouts during local development.
* High-speed execution profiles within CI pipelines.
* Distinct separation of failures across different fields.

---

### 4) Input Sanitization and Data Flattening (`_normalize_value`)

Incoming test criteria and exception states can manifest as diverse types:

* `None`
* `UNSET` sentinels
* Tuples (representing multi-line chunks)
* Native strings or arbitrary objects

The normalization layer guarantees:

* Consistent and predictable comparison streams.
* Crash-safe operations over text blocks.
* Uniform behavior regardless of the underlying data type.

---

### 5) Specialized Textual Inspection (`compare_strings`)

This internal component serves as the core engine for all string-based assertions:

* Routes variables through the multi-mode evaluation gates (fuzzy, prefix, exact).
* Leverages data sanitization to abstract type variance.
* Maintains a clean, deterministic execution path.

---

## 🔍 Usage Examples

### Validating a Single Attribute

```python
assert_exception_fields(subtests, exc, message="Boom")
```

### Validating Multiple Attributes Simultaneously

```python
assert_exception_fields(
    subtests,
    exc,
    error_name="VALUE_ERROR",
    label="user_id",
    expected="non-empty",
    exact_match=True,
)
```

### Prefix-Based Validation (Prefix Match)

```python
assert_exception_fields(subtests, exc, message="Invalid", startswith=True)
```

### Fuzzy Substring Matching

```python
assert_exception_fields(subtests, exc, problem="token")
```

### Silent Execution Mode

```python
assert_exception_fields(subtests, exc, message="Boom", verbose=False)
```
